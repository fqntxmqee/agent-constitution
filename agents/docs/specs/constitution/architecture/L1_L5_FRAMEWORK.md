# AI 时代的软件需求与资产标准化框架（L1-L5）

> **版本**: V2.0  
> **生效日期**: 2026-04-11  
> **前序版本**: V1.0 (L1-L4)  
> **状态**: 建设中

---

## 一、背景与目标

本框架旨在解决"一句话需求"或"多轮对话"到标准化系统资产的转化问题。通过 L1-L5 五层架构，结合 OpenSpec 规范，实现：

1. **消除歧义**：业务语言 → 技术语言的无损转换
2. **资产复用**：新需求优先通过"搭积木"复用现有功能点
3. **文档即代码**：利用 AI 反向生成，保证需求与实现的一致性
4. **结构化验证**：L5 测试点层提供从功能契约到场景验收的完整验证链路

### V2.0 主要变更

| 变更项 | V1.0 (L1-L4) | V2.0 (L1-L5) |
|--------|--------------|--------------|
| L3 定义 | 业务活动（不区分前后端） | L3-BE 业务活动 + L3-FE 页面/组件 |
| 验证层 | 无 | L5 测试点层（双绑定） |
| 稳定性 | 未定义 | 五级稳定性梯度 |
| 验收依据 | 扁平 AC 文档 | L5 测试点套件 |

## 二、五层架构定义

### 层级总览

| 层级 | 名称 | 含义 | 稳定性 | 变更审批 |
|------|------|------|--------|---------|
| L1 | 领域 (Domain) | 业务边界 / Bounded Context | 极高（几乎不变） | 需架构评审 |
| L2 | 场景 (Scenario) | 业务价值流，用户的完整目标 | 高 | 需产品确认 |
| L3 | 活动/页面 (Activity/Page) | L3-BE=业务活动，L3-FE=页面/组件 | 中 | 需求级审批 |
| L4 | 功能点/模块 (Function Point) | 最小可复用技术单元 | 低（频繁重构） | 开发自主 |
| L5 | 测试点 (Test Point) | 确定性验证锚点（功能契约 + 验收标准） | 中高 | 需验收确认 |

### L1：领域层 (Domain)

**定义**：业务边界。代表一个完整的业务子系统或 Bounded Context，拥有独立的数据模型和业务规则。

**稳定性**：极高 -- 领域边界一旦确立几乎不变，变更意味着业务模型根本性调整。

**示例**：
- 交易域 (Trade)
- 商品域 (Product)
- 库存域 (Inventory)
- 用户域 (User)
- 营销域 (Marketing)

**AI 作用**：领域划分助手，分析代码库模块依赖，自动识别和校验领域边界是否清晰。

---

### L2：场景层 (Scenario)

**定义**：业务价值流。在特定领域下，用户为了达成某个完整目标所经历的一系列交互集合。

**稳定性**：高 -- 场景代表核心业务流程，新增场景常见但已有场景很少被删除。

**示例**：
- 交易下单 (Place Order)
- 订单管理 (Order Management)
- 购物车结算 (Cart Checkout)
- 售后退款 (After-sales Refund)

**AI 作用**：场景聚类，将分散的用户故事（User Stories）自动归类到标准场景下，识别缺失的场景覆盖。

---

### L3：活动/页面层 (Activity / Page)

L3 拆分为两个子层，分别对应后端和前端视角：

#### L3-BE：业务活动 (Business Activity)

**定义**：后端行为原子。场景中的具体后端步骤，具有明确的输入、输出和状态变更。

**稳定性**：中 -- 业务流程调整时会新增、合并或拆分活动节点。

**示例**：
- 下单提交 (Order Submission) -- 输入：购物车快照；输出：订单号；状态变更：库存锁定
- 库存预占 (Stock Reserve) -- 输入：SKU + 数量；输出：预占凭证；状态变更：可售库存扣减
- 支付回调处理 (Payment Callback) -- 输入：支付通知；输出：订单状态更新；状态变更：已支付

**AI 作用**：流程挖掘，通过日志或代码调用链，自动还原业务活动流程图，识别冗余或缺失的活动节点。

#### L3-FE：页面/组件 (Page / Component)

**定义**：前端交互单元。场景中的具体页面或核心组件，具有用户交互逻辑和渲染逻辑。

**稳定性**：中 -- UI 改版、交互优化时会频繁调整。

**示例**：
- 商品详情页 (Product Detail Page) -- 交互：加购、收藏、分享；渲染：商品图片轮播、规格选择
- 购物车结算页 (Cart Checkout Page) -- 交互：数量修改、优惠券选择、提交；渲染：价格明细、地址卡片
- 订单列表页 (Order List Page) -- 交互：筛选、搜索、分页；渲染：订单卡片、状态标签

**AI 作用**：页面结构分析，通过组件树和路由配置，自动识别页面层级和组件复用关系。

#### L3-BE 与 L3-FE 的关系

同一个 L2 场景下，L3-BE 和 L3-FE 是平行关系而非从属关系。它们通过 L4 功能点建立间接关联：

```
L2 交易下单
  ├── L3-BE 下单提交 ──→ L4 库存校验 ←── L3-FE 购物车结算页
  ├── L3-BE 库存预占 ──→ L4 商品查询 ←── L3-FE 商品详情页
  └── ...
```

---

### L4：功能点/模块层 (Function Point / UI Module)

**定义**：最小可复用技术单元。跨领域复用的具体逻辑计算、数据操作或 UI 组件，是动态编排的"积木"。

**稳定性**：低 -- 实现层频繁重构、优化，但对外契约（输入输出 Schema）应保持稳定。

L4 涵盖后端和前端两类：

| 类型 | 说明 | 示例 |
|------|------|------|
| 功能点 (Function Point) | 后端服务能力，对应具体函数/API | `get_product_detail`, `check_stock_status`, `calculate_coupon` |
| UI 模块 (UI Module) | 前端可复用组件 | 商品卡片组件、价格计算器组件、地址选择器组件 |

**跨域引用**：L4 的归属权属于其定义域。例如 `get_product_detail` 属于商品域，但可被订单域的 L3 活动引用。引用时在订单域上下文中称为"商品子域"的能力。

**AI 作用**：代码逆向工程，阅读代码，自动提取函数逻辑，抽象为标准功能点，并建立索引。

---

### L5：测试点层 (Test Point)

**定义**：确定性验证锚点。L5 是测试的结构化聚合层，不是最末端的叶子节点。层级关系为：

**L3/L4 → L5 测试点（按分类聚合） → 测试用例（具体 case）**

**稳定性**：中高 -- 测试点是验证锚，但会跟随需求调整而增减或修订，稳定性介于场景（L2）与活动（L3）之间。

#### 双绑定模式

L5 通过两种绑定模式覆盖不同粒度的验证需求：

| 绑定目标 | 绑定名称 | 含义 | 示例 |
|----------|---------|------|------|
| L4 功能点 | 功能契约 (Contract) | 函数级输入/输出/不变量断言 | `test_calculate_coupon_threshold`、`test_cart_render_empty_state` |
| L3 活动/页面 | 验收标准 (Acceptance) | 场景级验收条件 | "用户 3 步内完成结算"、"支付回调 5s 内处理" |

#### 测试点分类

同一 L4 功能点下的测试点按类型分组，便于按维度检查覆盖度：

| 分类 | 关注点 | 示例 |
|------|--------|------|
| 交互类 | 用户操作路径、边界行为 | 测试空购物车提交、超量加购 |
| 性能类 | 响应时间、吞吐量、资源占用 | 测试商品查询 P99 延迟 < 200ms |
| 逻辑类 | 业务规则正确性、计算精度 | 测试优惠券叠加计算、库存扣减一致性 |
| 安全类 | 权限校验、注入防护、数据脱敏 | 测试越权访问他人订单、SQL 注入 |

分类维度可按项目需要扩展（如兼容性类、无障碍类等）。

#### 跨域引用规则

L5 测试点的归属跟随 L4，不跟随引用方。例如"商品查询"的测试点属于商品域，即使该功能点被订单域引用，测试点仍然维护在商品域下。

---

### 完整实例：交易订单渲染

以交易下单场景为例，展示 L2 → L3 → L4 → L5 → 测试用例的完整链路：

```
L1 交易域
  └── L2 交易下单
        ├── L3-BE 订单渲染（业务活动）
        │     ├── L4 商品查询（跨域引用：商品子域）
        │     │     ├── L5 测试点 [交互类] → 用例: 查询不存在商品、批量查询上限...
        │     │     ├── L5 测试点 [性能类] → 用例: P99 < 200ms、并发 1000 QPS...
        │     │     ├── L5 测试点 [逻辑类] → 用例: 多规格商品返回、下架商品过滤...
        │     │     └── L5 测试点 [安全类] → 用例: 商品 ID 注入、未授权访问...
        │     ├── L4 库存校验
        │     │     └── L5 测试点 [逻辑类] → 用例: 超卖校验、预占回滚...
        │     └── L5 测试点 [验收级: 订单渲染完整性]
        │           → 用例: 渲染包含商品+库存+价格、缺货商品标灰、价格一致性...
        │
        └── L3-FE 订单渲染页面
              ├── L4 商品卡片组件
              │     ├── L5 测试点 [交互类] → 用例: 点击跳转详情、长按预览...
              │     └── L5 测试点 [逻辑类] → 用例: 价格格式化、库存状态显示...
              └── L5 测试点 [验收级: 页面渲染正确性]
                    → 用例: 首屏加载 < 1s、骨架屏展示、空态处理...
```

## 三、L5 测试点套件与验收关联

### 套件定义

**L5 测试点套件** = 某个 L3 直接关联的 L5 测试点 + 该 L3 下属所有 L4 关联的 L5 测试点。

套件是验收智能体的结构化验收依据，替代原有的扁平 `acceptance-criteria.md`。

### 套件聚合方式

```
L3-BE 订单渲染 的 L5 套件:
  ├── [验收级] 订单渲染完整性          ← L3 直接关联
  ├── [交互类] 商品查询-交互           ← L4 商品查询关联
  ├── [性能类] 商品查询-性能           ← L4 商品查询关联
  ├── [逻辑类] 商品查询-逻辑           ← L4 商品查询关联
  ├── [安全类] 商品查询-安全           ← L4 商品查询关联
  └── [逻辑类] 库存校验-逻辑           ← L4 库存校验关联
```

### 迭代累积机制

L5 套件跨迭代持续累积，不因单次需求而重建：

| 操作 | 说明 |
|------|------|
| 追加 | 新需求产生新测试点/用例，追加到对应套件 |
| 修订 | 需求变更导致已有测试点调整，更新并标记版本 |
| 废弃 | 功能下线时标记测试点为"已废弃"，不删除 |

每个测试点携带版本标记（如 `v1.0`, `v1.1`），修订时保留变更历史。

### 验收智能体集成

验收智能体以 L5 套件为主要验收依据，执行双源验证：

| 验证源 | 类型 | 验证方式 | 输出 |
|--------|------|---------|------|
| L5-Acceptance（绑定 L3） | 人可读验收标准 | 智能体逐条比对交付物 | 通过/失败清单 |
| L5-Contract（绑定 L4） | 机器可执行契约测试 | 检查测试执行结果 | 测试通过率 |

验收报告新增字段：
- L5 套件覆盖度（已验证测试点 / 套件总测试点）
- 各分类维度通过率（交互类 100%、性能类 95%、...）

## 四、核心机制：动态编排与双向映射

### 4.1 正向路径：需求落地 (Business → Code)

```
1. 定位场景 (L2)：明确需求属于哪个场景
      ↓
2. 拆解活动/页面 (L3)：
   - 判定前后端归属：L3-BE（业务活动）或 L3-FE（页面/组件）
   - 同一需求可能同时产生 L3-BE 和 L3-FE
      ↓
3. 编排功能点 (L4)：
   - 复用：从功能点库中检索现有能力
   - 扩展/新增：定义新功能点
   - 生成编排 DSL：规定功能点的执行顺序、参数传递
      ↓
4. 生成测试点 (L5)：
   - 绑定 L4：为新增/变更的功能点生成分类测试点（交互、性能、逻辑、安全）
   - 绑定 L3：为 L3 活动/页面生成验收级测试点
   - 复用检查：检索已有测试点，避免重复
      ↓
5. 代码生成/组装：AI 根据编排 DSL 自动组装代码 + 测试骨架
```

### 4.2 反向路径：资产治理 (Code → Business)

```
1. 代码扫描：AI Agent 定期扫描领域下的代码仓库
      ↓
2. 语义提取：
   - 识别独立的 Service 方法或 API 接口
   - LLM 分析业务语义
   - 归属判断：属于哪个 L3 业务活动？
      ↓
3. 功能点注册 (L4)：
   - 已存在 → 更新元数据
   - 新能力 → 自动创建，标记"待审核"
      ↓
4. 测试覆盖缺口检测 (L5)：
   - 扫描已注册功能点的测试覆盖情况
   - 标记无测试点的 L4 为"测试缺口"
   - 生成缺口报告，建议补充的测试点分类
      ↓
5. 图谱更新：自动更新 L2→L3→L4→L5 依赖图谱
```

## 六、功能点与测试点向量库（建设中）

### 目的

防止 AI 每次都"重新发明轮子"，通过 RAG 检索现有功能点和测试点。

### 功能点检索

1. **向量化**：将所有 L4 功能点的语义描述存入向量数据库
2. **检索**：新需求进来时，先检索相似度 > 0.85 的现有功能点
3. **决策**：
   - 能复用 → 直接编排
   - 需扩展 → 扩展功能点定义
   - 需新增 → 新建功能点 + 编排

### 测试点检索（规划中）

1. **向量化**：将 L5 测试点的签名和描述存入向量数据库
2. **检索**：新功能点创建时，检索相似功能点的测试点作为参考模板
3. **决策**：
   - 可复用 → 关联已有测试点
   - 需定制 → 基于模板生成新测试点
   - 全新场景 → 按分类维度生成测试点骨架

## 七、稳定性模型

### 稳定性梯度

```
L1 (极高) > L2 (高) > L5 (中高) > L3 (中) > L4 (低)
```

**设计原理**：
- **L1 领域**：业务边界一旦确立，几乎不会变更。变更意味着整个业务模型重构。
- **L2 场景**：核心业务流程稳定，但会随业务发展新增场景。
- **L5 测试点**：作为验证锚点，稳定性高于被测对象（L3/L4），但会跟随需求调整。不是"不动锚点"，而是"惰性变更" -- 只有当业务规则变化时才更新。
- **L3 活动/页面**：业务流程调整、UI 改版时会变化。
- **L4 功能点**：实现层最频繁变更，重构、优化是常态。

### 变更影响链

层级越高，变更的影响范围越大：

| 变更层级 | 影响范围 | 审批要求 |
|----------|---------|---------|
| L1 变更 | 影响该域下所有 L2-L5 | 架构评审 + 产品确认 |
| L2 变更 | 影响该场景下所有 L3-L5 | 产品确认 |
| L3 变更 | 影响关联的 L4 + L5 | 需求级审批 |
| L4 变更 | 影响关联的 L5 测试点 | 开发自主，但需更新 L5 |
| L5 变更 | 仅影响测试用例 | 验收确认 |

## 八、实施策略

### 阶段一：构建功能点知识库

- 输入：现有 Git 代码库
- AI 任务：遍历 Service 层方法，生成 L4 功能点清单
- 产出：{ID, 名称, 业务描述, 代码路径, 输入输出 Schema}

### 阶段二：建立活动与编排映射

- 输入：历史需求文档 + 代码调用链
- AI 任务：将 L4 功能点聚合成常见的执行序列
- 产出：L3 业务活动库及标准编排模板

### 阶段三：构建测试点基线

- 输入：已有测试用例 + L4 功能点清单
- AI 任务：将已有测试用例归类到 L5 测试点，识别测试缺口
- 产出：L5 测试点套件基线 + 覆盖缺口报告

### 阶段四：需求驱动的自动化闭环

- 输入：自然语言需求
- AI 任务：解析 → 匹配 → 缺口分析 → 生成（含 L5 测试骨架）
- 产出：标准化编排配置文件 + 骨架代码 + 测试骨架
